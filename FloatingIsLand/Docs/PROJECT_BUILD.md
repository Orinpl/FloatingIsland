> 本文档基于 [GAME_DESIGN.md](GAME_DESIGN.md) 制定，描述如何在当前 Unity 工程中从零构建本游戏：技术选型、架构分层、目录规划、系统拆解、数据配置方案、里程碑计划、测试与验收映射。

| 版本管理 | Git（main 分支） |

### 1.2 技术选型决策

| 决策点 | 选型 | 理由 |
|---|---|---|
| 地图模型 | **方格网格 + 整数高度层 + 3D 表现层**：格子坐标 `(x, z, layer)`，高低台地是不同层（设计 §5.1/§21 决策 25）；影响范围按**球形三维欧氏距离**判定（§21 决策 26） | 设计中风只有八方向、45° 转向，方格网格的 8 邻接与之一一对应；高低差是规则（不只是表现），球形范围让高台与平原建筑能跨层互相影响 |
| 网格表现/摆放交互 | **浅接入 Easy Grid Builder Pro 2**（已购插件，Assets/SoulGames）：只用它的网格渲染、鼠标选格吸附、ghost 预览；校验/占用/计分真相全在领域层（详见 [GRID_INTEGRATION.md](GRID_INTEGRATION.md)） | 插件无外部校验钩子、占地只支持矩形、格子无地形槽——当真相用会跟 L 形占地/地形规则打架；只当"表现外设"用则零冲突，且吃掉最值钱的交互层 |
| 逻辑与表现分离 | 核心规则全部写成**不依赖 UnityEngine 的纯 C# 逻辑层**，MonoBehaviour 只做表现与输入 | 设计验收 25 条几乎全是规则判定，纯逻辑层可用 EditMode 单测逐条覆盖，不开 Play Mode 就能验证 |
| 数值配置 | **Excel 配表工具链 TableTool**（xlsx → JSON + 强类型 C#，已落地，见 [CONFIG_TABLES.md](CONFIG_TABLES.md)；替代早期 ScriptableObject 方案） | 设计 §20 要求所有数值可调；关系矩阵这类大表在 Excel 里比 Inspector 好维护，转表/校验零代码 |
| 相机 | MVP：自制编辑器式自由相机（`GameplayCameraController`：WASD 平移、Shift/Ctrl 升降、滚轮缩放、右键旋转、中键平移）；Cinemachine 留待需要环绕预设/镜头混合时再引入 | 规划建造玩法需要编辑器式自由视角，轻量脚本即可；Cinemachine 已装包，后续可无缝升级 |
| 输入 | Input System（新输入系统） | 已装包；摆放/旋转/取消/相机操作用 Action Map 管理 |
| UI | uGUI + TextMeshPro | 已装包；MVP 阶段 UI 量小，不引入额外框架 |
| 随机数 | 全局带种子的随机服务 | 地图生成、建筑组抽取都走同一可复现种子，便于复盘和测试 |

## 2. 架构总览

自底向上四层，依赖只允许向下：

```
┌─────────────────────────────────────────────┐
│  Presentation 表现层 (MonoBehaviour)          │
│  地图渲染 / 建筑模型 / 风流特效 / UI / 输入      │
├─────────────────────────────────────────────┤
│  Application 应用层                           │
│  GameSession 局内流程 / 摆放流程 / 预览请求      │
├─────────────────────────────────────────────┤
│  Domain 领域层（纯 C#，零 Unity 依赖）          │
│  地图状态 / 风模拟 / 计分引擎 / 物流结算 /        │
│  合法性校验 / 等级与建筑组 / 终局结算             │
├─────────────────────────────────────────────┤
│  Config 配置层 (Excel 配表 → JSON → 强类型 Tables) │
│  建筑定义 / 关系矩阵 / 风参数 / 等级表 / 全局参数  │
└─────────────────────────────────────────────┘
```

关键原则：

1. **领域层是唯一真相**。风路怎么走、每一分从哪来，只由领域层计算；表现层只读结果，绝不自己算分。
2. **配置在进入领域层前转成纯数据快照**，领域层不直接依赖 `Tables` 静态类（`Game.Domain` 不引用 `Game.Config`），保证可单测、可序列化。
3. **事件驱动的表现更新**。领域层每次状态变更（建筑落地、风路重算、覆盖变化）发出领域事件，表现层订阅刷新，避免每帧轮询。
4. **计分产出"分数明细"而不是一个总数**。每次结算返回逐条来源列表（基础分 / 地形 / 某栋邻居 / 物流覆盖 / 惩罚…），直接喂给 §7.4 的预览 UI，也直接喂给单测断言。

## 3. 目录结构规划

```
Assets/
├── Scenes/
│   ├── Boot.unity              # 常驻启动场景（AppRoot/UIRoot，见 BOOT_FRAMEWORK.md）
│   ├── Main.unity              # 主玩法场景（附加加载，每关整体重载）
│   └── Sandbox.unity           # 规则调试沙盒场景
├── Script/
│   ├── Domain/                 # 纯 C# 领域层（asmdef: Game.Domain，noEngineReferences）
│   │   ├── Map/                # 网格、地形、地图元素、地图生成
│   │   ├── Wind/               # 风流传播、交汇合成（见 WIND_IMPL.md）
│   │   ├── Building/           # 建筑实例、合法性校验、锚点归属
│   │   ├── Scoring/            # 计分引擎、分数明细、终局结算
│   │   ├── Logistics/          # 物流覆盖、物流风、物流中心强化
│   │   ├── Progression/        # 关卡/组进度、建筑组抽取、分数门槛、结束判定
│   │   └── Common/             # 方向、坐标、种子随机、领域事件
│   ├── Config/                 # SO 定义 + 快照转换（asmdef: Game.Config）
│   ├── App/                    # GameSession、摆放流程状态机（asmdef: Game.App）
│   ├── View/                   # 地图/建筑/风/覆盖的渲染（asmdef: Game.View）
│   ├── ViewEGB/                # EGB Pro 2 适配层（无 asmdef，编入 Assembly-CSharp，见 GRID_INTEGRATION.md）
│   ├── UI/                     # HUD、建筑组选择、分数预览面板（asmdef: Game.UI）
│   └── Input/                  # Input System 封装（asmdef: Game.Input）
├── Resources/Tables/           # 转表产物 JSON（正本：仓库根 Tables/FloatingIsland.xlsx，见 CONFIG_TABLES.md）
├── Prefabs/
│   ├── Tiles/                  # 地块表现预制体
│   ├── Buildings/              # 建筑表现预制体（MVP 阶段用几何体白模）
│   └── FX/                     # 风流线、覆盖高亮
├── Tests/
│   └── EditMode/               # 领域层单元测试（asmdef 引用 Game.Domain）
└── Tool/                       # 编辑器工具（地图预览、配置校验器）
```

asmdef 依赖方向：`UI / View → Input → App → Domain ← Config`。`Game.Domain` 勾选 *No Engine References*，从编译层面禁止领域层引用 UnityEngine。

`UI / View → Input` 这条是接入手机端时加的：指针位置、触屏手势、当前是鼠标还是手指，三样都由 `Game.Input` 的 `PointerInput` 统一提供（§11.1）。反向不成立——输入层不认识摆放与 HUD。需要**双向**通信的两处（滚轮归属仲裁、摆放预览结论）仍然只能放共同上游 `Game.App`：`InputArbiter`、`BuildPreviewState`、`BuildCommandBus`。

## 4. 核心系统拆解

按设计文档章节映射到模块，含各系统的实现要点与依赖顺序。

### 4.1 地图系统（设计 §5）→ `Domain/Map`

- **网格模型**：方格坐标 `(x, z, layer)`（layer 为整数高度层，设计 §21 决策 25），每格持有——地形类型（空岛/绿地/矿藏/浮空/虚空）、建筑占用、途经风段列表。风路挂在格子上但不占建筑位（设计 §5.1）。
- **范围判定**：统一走球形三维欧氏距离（`√(dx²+dz²+(Δlayer×层高折算系数)²) ≤ radius`，设计 §21 决策 26）；层高折算系数进 GameConfig（待数值化）。注意斜向 1 格距离为 √2，半径数值要按欧氏口径拍。
- **地图元素**：巨型风车（唯一）、锚点、矿藏、绿地、初始风源、浮空区域，作为生成期写入的静态元素。
- **地图生成器**：接收种子 + 生成参数（各元素数量区间来自配置），输出完整初始地图。MVP 可以先做 2～3 张手工布局的固定地图，随机生成放到 M6（验收第 1 条要求随机生成，但手工图能先支撑规则验证）。

### 4.2 风系统（设计 §8、§9）→ `Domain/Wind`

整个项目**规则最重、必须最先做对**的系统。

实现设计详见 [WIND_IMPL.md](WIND_IMPL.md)，要点：

- **叠加场模型**：风与风互不影响——每股风只受建筑（风帆、物流点）影响，独立走完自己的路径；交汇格的可见风向/风力由该格全部途经风段向量合成得到，只用于显示与计分，不改变任何风道。重算 = 两遍扫描（逐股独立传播 → 逐格合成），无迭代、与处理顺序无关。
- **风的表示**：风源列表 + 全图重算。每次影响风的操作（放风帆、放物流点）后全量重跑——逻辑简单、无累积误差，MVP 地图规模（预计 ≤ 64×64）下性能完全够。
- **传播规则**：沿当前方向逐格推进，每格消耗 1 段风长（斜向同价）；遇风帆按该风帆的左/右 45° 设定转向（不恢复风长，重复经过不限次）；遇物流点标记为物流风并按限制延长（同点不重复、每股最多两次，设计 §10.5）。允许自交与绕圈；终止由风长有界保证（总路径 ≤ 初始长度 + 延长上限），不需要循环截断。
- **交汇合成（设计 §8.5–8.6）**：同格全部风段按"强度 × 八方向单位向量"求和——风力为模长四舍五入、上限 5，方向 45° 吸附、22.5° 平局取顺时针侧；风长不受交汇影响。§8.5 示例表全部固化为单元测试用例。
- **对外输出**：`每格 → [方向, 风力, 是否物流风]` 的查询接口，供计分、居民区惩罚、船坞收益、表现层箭头渲染共用。

### 4.3 建筑系统（设计 §6、§11、§12）→ `Domain/Building`

- **建筑定义全部来自配置**（见 §5 数据方案），领域层只认建筑 ID + 规则数据，不为每栋建筑写子类；特殊行为（风帆转向、物流点、锚点归属）以"能力标签"挂在定义上，由对应系统识别。
- **合法性校验器**：按定义检查——地形要求（农田→绿地、船坞→浮空区、风帆→有风格、采矿站→矿藏范围内）、占位冲突。返回**具体的非法原因**（供 §7.4 预览高亮）。
- **锚点归属（设计 §12.8）**：船坞落地时按"最近优先、同距取归属数少者"绑定唯一锚点，并按序号套 100%/50%/25%/0% 递减表。

### 4.4 计分引擎（设计 §7、§13～§18）→ `Domain/Scoring`

- **关系矩阵驱动**：真值表 A/B、地图元素交叉表、同类关系表全部转成配置数据（有向关系条目：受益建筑 × 来源建筑 → 分值/上限/半径引用）。计分引擎只做一件事：遍历落点范围内的对象，逐条匹配关系条目，累加成**分数明细**。
- **结算顺序**（对应设计 §7.1 列表）：基础分 → 地形 → 地图元素（巨型风车通用/专属替代逻辑在此处理）→ 有向邻接加减分（含数量上限，如居民区的计数上限表）→ 同类惩罚 → 物流专属邻接分（最多 2 个物流点）→ 物流覆盖分（去重，仅 1 次）→ 风力即时分（风向标乘法、船坞曲线、居民区强风惩罚）→ 特殊效果。
- **预览 = 干跑**：预览调用与真实结算同一条计分管线，只是不落地、不计分——保证"预览所见即所得"（验收第 4 条）。
- **终局结算（设计 §7.2）**：独立入口，按最终风路/物流状态重算船坞风能奖励与物流网络奖励，只加最终分数（设计 §3.3）。

### 4.5 物流系统（设计 §10）→ `Domain/Logistics`

- **覆盖状态统一**：本地范围覆盖与物流风覆盖合并为同一个"已接入物流"集合（HashSet 语义），天然保证基础覆盖分只算一次（设计 §10.3–10.4、验收第 16 条）。
- **物流中心**：不产生覆盖，只对指定五类建筑（势能塔/工坊/船坞/粮仓/居民区）发放专属分；自身按范围内物流点数量加分、同类大扣分。
- 覆盖集合在每次风路重算后同步刷新，作为领域事件广播给表现层画覆盖高亮。

### 4.6 等级与建筑组（设计 §3、§4）→ `Domain/Progression`

- 关卡/组进度（3 关，每关组数见 `Stage.groupCount`）、分数门槛解锁表、二选一建筑组抽取（主题化配方、同组可重复、保底规则）、刷新保护机制。
- **结束判定**：本关组数发完 / 无合法落点（对当前手牌全图扫描）/ 累计分不足以解锁且手牌为空 / 玩家主动收官，四条件任一触发本关结算；未达通关分则整局结束并进入上榜流程。

### 4.7 应用层 → `Script/App`

- **局外流程**：Boot → 主界面 → 加载 → 局内 → 结算 → 下一关/回主界面，由 `GameFlow` 状态机承载（已落地，详见 [BOOT_FRAMEWORK.md](BOOT_FRAMEWORK.md)；"下一关"= 换新地图新种子再开一局）。
- `GameSession`：串起"抽组 → 选组 → 逐栋摆放 → 结算发钱 → 解锁下一级"的核心循环状态机（设计 §1.3）。
- 摆放流程状态机：选中建筑 → 拖动预览（实时干跑计分 + 高亮）→ 风帆额外弹左/右转选择 → 确认落地 / 取消。

### 4.8 表现与 UI → `Script/View`、`Script/UI`

MVP 全部用白模和程序化表现，不等美术资源：

- **地图渲染**：地块用色块/简单 Mesh 区分地形；巨型风车、锚点、矿藏用几何体白模。网格线/选格吸附/ghost 预览浅接入 EGB Pro 2（[GRID_INTEGRATION.md](GRID_INTEGRATION.md)）。
- **风渲染**：每格风段画方向箭头，颜色映射风力等级（1～5），物流风加描边/变色；这是玩家读懂风系统的关键，投入优先级高于建筑外观。
- **UI 清单（MVP）**：顶部关卡条、左下计分区（总分/通关进度/组序）、建筑组二选一面板、手牌栏、摆放预览明细面板（逐条分数来源，设计 §7.4）、非法原因提示、结算面板（含上榜）、主界面排行榜。

## 5. 数据配置方案（对应设计 §20）

已落地为 **Excel 配表工具链**（TableTool，用法见 [CONFIG_TABLES.md](CONFIG_TABLES.md)，替代早期 ScriptableObject 方案）：正本 `Tables/FloatingIsland.xlsx`，转表产出 `Assets/Resources/Tables/*.json` + 强类型 `Tables.g.cs`，由启动框架的 Boot 状态统一加载。设计 §20 的全部待数值化项收敛为 9 张表：

| 表 | 内容 | 对应设计章节 |
|---|---|---|
| **Building** | 建筑定义：占地形状、地形要求、基础分、作用半径、风力收益/惩罚曲线、孤立惩罚、开发批次 | §11、§12、§19 |
| **BuildingRelation** | 建筑×建筑有向邻接加/扣分（真值表 A/B + 单向/双向/负面表数据化；来源=自己表示同类关系） | §13、§15～§18 |
| **BuildingMapElement** | 建筑×地图元素加分（含巨型风车专属替代条目） | §6、§14 |
| **MapElement** | 地图元素定义、有效范围、生成数量区间 | §5、§6 |
| **WindLevel** | 风力 0~5 级与通用倍率 | §8 |
| **Level** | 局内 20 级：解锁费用、建筑组数量、组大小（组的成员配方在 BuildingGroupTheme） | §4 |
| **GameConfig / WindConfig / LogisticsConfig**（单例参数组） | 全局计分/保护机制/锚点递减、初始风参数、物流覆盖与延长参数 | §3、§8、§10、§20 |

配套校验：

1. **转表期校验**（已有）：TableTool `check`（结构/主键/引用完整性）+ ConfigVerify 冒烟（脱离 Unity 编译读表层并真实加载全部 JSON）。
2. **规则级校验器**（待补，放 `Assets/Tool`）：检查关系表与真值表一致性（如"双向关系必须在两个方向各有一条"、"§21 已确认决策不被配置违反"），一键报告。
3. **数值总览窗口**（待补）：把 BuildingRelation 汇总回真值表形态展示，供策划对照设计文档核对。

## 6. 里程碑计划

每个里程碑以"可运行/可测试的交付物"收口，M1～M4 是纯逻辑优先，表现层最小化。

### M0 · 工程骨架（0.5 周）—— 大部分已完成

- ✅ 目录结构与 asmdef（9 个，含 Editor/Tests；`Game.Domain` 关闭引擎引用）；
- ✅ Boot/Main 双场景 + 局外流程状态机 GameFlow + 骨架 UI（一键生成：Tools → 框架 → 生成启动场景；详见 [BOOT_FRAMEWORK.md](BOOT_FRAMEWORK.md)）；
- ✅ 配表工具链与 9 张表初版（[CONFIG_TABLES.md](CONFIG_TABLES.md)）；
- ✅ EditMode 冒烟测试；
- ⬜ Sandbox 场景、Cinemachine 环绕相机、Input Action Map（M1 摆放交互前补）；

## 7. 测试策略

### 7.1 EditMode 单元测试（主力）

领域层零引擎依赖，规则全部用单测锁定。必测清单：

- **风**：直线传播长度耗尽（斜向一步同价）；风帆左/右转向；§8.5 交汇合成示例表逐条；单位向量权重一致性；5 级封顶；22.5° 平局顺时针吸附；抵消只在重叠格（越过对方终点后恢复）；交汇不改风长；自交自增强；风帆重复经过且必然终止；物流点延长的两条限制。
- **计分**：真值表 A/B 抽样逐条（至少覆盖每种符号各一例）；单向关系不反向生效（工坊给风车加分、风车不给工坊加分）；巨型风车专属替代通用；居民区计数上限表；同类惩罚。
- **物流**：双物流点覆盖同一建筑只算一次覆盖分；本地覆盖与物流风覆盖不叠加；专属分与覆盖分叠加；物流中心只强化指定五类。
- **船坞**：锚点归属两条规则；递减表 100/50/25/0；0 级风惩罚；孤立惩罚。
- **进程**：分数门槛是准入不是消耗；负分同样计入总分；四种结束条件；跨关分数保留。

### 7.2 配置校验（编辑器工具）

每次改配置资产后一键校验：关系表对称性、§21 的 18 条已确认决策不被违反、数值缺失检测。

### 7.3 沙盒场景手测

Sandbox 场景提供作弊面板：直接加分、跳组、任意刷建筑、手动放风源——用于快速搭出边界场景（多风合流、超长物流链）做人工验证。

## 11. 输入与出包（PC / 手机双端）

### 11.1 一套玩法，两套操作

同一份玩法代码同时供 PC 与手机。**没有任何规则、算分、落点逻辑分平台**——两端的差别只有「怎么指到一个格子」和「怎么说确认」，全部收敛在 `Game.Input/PointerInput.cs` 一个文件里。

|          | PC                | 手机                        |
|----------|-------------------|-----------------------------|
| 移动视角 | WASD / 中键拖     | 单指拖                      |
| 缩放     | 滚轮              | 双指捏合                    |
| 旋转视角 | 右键拖            | 双指转（偏航）/ 双指上下拖（俯仰） |
| 指向格子 | 光标悬停          | 点一下（点到哪停在哪）      |
| 落地     | 左键              | 再点同一格 / 点「建造」按钮 |
| 建筑转 90° | 滚轮            | 点「旋转」按钮              |
| 取消     | Esc               | 点「取消」按钮              |

三条关键取舍：

- **触屏的「悬停」是黏性的。** 触屏没有 hover 这回事，所以 `PointerInput` 把「指针指着哪」定义成「最近一次点击的位置」，手指抬起后不清除。这样范围环 / 邻居辉光 / 飘分数字在手指离开屏幕后还留着——手指不挡视线，玩家才看得清这一摆值多少分。
- **落地要点两下。** 第一下选落点，再点同一格才建。手机误触没有 Esc 可救，而建筑落地即结算、不可回退（见 `BuildBoardTests` 的「已落地建筑的分数不回溯」）。判定与边界见 `TouchGestureTests`。
- **UI 遮挡判定按位置做射线，不看 pointerId。** `EventSystem.IsPointerOverGameObject()` 的**无参**重载查的是鼠标（pointerId = -1），手指恒返回 false；带 id 的重载又对不上号（这里读新输入系统的 touchId，uGUI 的 StandaloneInputModule 走旧输入的 fingerId）。所以统一用 `PointerInput.IsOverUI(屏幕坐标)`，两端同一套判定。不改这条，手机上「点手牌按钮」会连带在按钮背后建一栋楼。

跨程序集的三个接缝（都在 `Game.App`，理由见 §3 的依赖方向说明）：`InputArbiter`（滚轮归属）、`BuildCommandBus`（HUD 按钮 → 摆放）、`BuildPreviewState`（摆放结论 → HUD，触屏「建造」按钮灰不灰靠它）。

**在 PC 上验手机操作**：`Tools/调试/触屏模拟（把鼠标当手指）`。开了之后编辑器按触屏规则跑，鼠标当一根手指用。双指手势（捏合、双指转）验不了，只能上真机。

### 11.2 出包

`Tools/打包/` 菜单，或 `Tools/打包/打包设置…` 打开面板：

| 菜单 | 做什么 |
|---|---|
| 同时打包 Windows + Android | 顺次出两个包，完成后切回原来的目标平台 |
| 只打 Windows x64 | Mono 后端（本机没装 Windows IL2CPP 模块） |
| 只打 Android APK / AAB | APK 装机调试，AAB 上架 |
| 配置安卓工具链 | 把 JDK / SDK / NDK 路径写进 EditorPrefs |
| 打开产物目录 | — |

- **不打 AssetBundle。** 本工程资源走 Resources / 直接引用，没有 AB 环节。
- **产物默认在工程目录旁的 `Build/`**（Assets 外，不会被 Unity 导入）。路径与打包选项存 EditorPrefs，按机器走，不进版本库。
- **安卓工具链**：本机 Android 模块不含 SDK/NDK/JDK，路径指向 `D:\Unity\{OpenJDK,SDK,NDK}`（JDK 11.0.14 / SDK platforms 34-36 + build-tools 34 / NDK 23.1.7779620，正是 2022.3 要的版本）。换机器在打包面板里改。
- **安卓打包会顺手改这几项工程设置**，面板上原样列着：包名 → `com.floatingisland.game`、脚本后端 → IL2CPP（ARM64 的前提）、ABI → ARMv7 + ARM64（Play 强制 64 位）、最低版本 → API 24、versionCode 自增。横竖屏 / 图标 / 签名**不在这里改**——那是策划美术的决定，藏在打包流程里改只会让人找不着。
- **整条流程不弹任何对话框**（唯一例外是打包面板上要人点的「浏览…」）。本项目踩过 `DisplayDialog` 阻塞主线程、Unity 整个失去响应且程序侧点不掉的坑。
- **命令行出包**（CI / 不开编辑器）：
  ```
  Unity.exe -quit -batchmode -projectPath <工程> \
    -executeMethod FloatingIsLand.EditorTools.PlayerBuildPipeline.BuildAllCommandLine \
    [-outputRoot <目录>] [-aab] [-development]
  ```
