# 浮空风岛建造游戏 · 项目构建文档

> 本文档基于 [GAME_DESIGN.md](GAME_DESIGN.md) 制定，描述如何在当前 Unity 工程中从零构建本游戏：技术选型、架构分层、目录规划、系统拆解、数据配置方案、里程碑计划、测试与验收映射。
>
> 设计文档回答"游戏是什么"；本文档回答"按什么顺序、用什么结构把它做出来"。

## 1. 工程现状与技术选型

### 1.1 工程现状

| 项 | 值 |
|---|---|
| 引擎版本 | Unity 2022.3.62f2 (LTS) |
| 渲染管线 | 内置管线（未安装 URP；如需风流特效建议后续切 URP，见 §9 风险） |
| 已安装关键包 | Input System 1.14.0、Cinemachine 2.10.3、Splines 2.8.0、TextMeshPro 3.0.9、uGUI、Timeline、Visual Scripting |
| 现有目录 | `Assets/Scenes`、`Assets/Script`、`Assets/Tool`（均为空） |
| 版本管理 | Git（main 分支） |

### 1.2 技术选型决策

| 决策点 | 选型 | 理由 |
|---|---|---|
| 地图模型 | **逻辑六边形/方格网格 + 3D 表现层**（首选方格，八方向风与方格天然匹配） | 设计中风只有八方向、45° 转向，方格网格的 8 邻接与之一一对应；六边形只有 6 邻接，无法直接表达八方向风 |
| 逻辑与表现分离 | 核心规则全部写成**不依赖 UnityEngine 的纯 C# 逻辑层**，MonoBehaviour 只做表现与输入 | 设计验收 25 条几乎全是规则判定，纯逻辑层可用 EditMode 单测逐条覆盖，不开 Play Mode 就能验证 |
| 数值配置 | **ScriptableObject 配置资产**（建筑表、风参数、等级表、全局计分参数） | 设计 §20 要求所有数值可调；SO 支持策划在 Inspector 直接改，不改代码 |
| 相机 | Cinemachine 俯视/环绕相机 | 已装包，ISLANDERS 式环绕视角开箱即用 |
| 输入 | Input System（新输入系统） | 已装包；摆放/旋转/取消/相机操作用 Action Map 管理 |
| UI | uGUI + TextMeshPro | 已装包；MVP 阶段 UI 量小，不引入额外框架 |
| 随机数 | 全局带种子的随机服务 | 地图生成、建筑组抽取都走同一可复现种子，便于复盘和测试 |

## 2. 架构总览

自底向上四层，依赖只允许向下：

```
┌─────────────────────────────────────────────┐
│  Presentation 表现层 (MonoBehaviour)          │
│  地图渲染 / 建筑模型 / 风流特效 / UI / 输入      │
├─────────────────────────────────────────────┤
│  Application 应用层                           │
│  GameSession 局内流程 / 摆放流程 / 预览请求      │
├─────────────────────────────────────────────┤
│  Domain 领域层（纯 C#，零 Unity 依赖）          │
│  地图状态 / 风模拟 / 计分引擎 / 物流结算 /        │
│  合法性校验 / 等级与建筑组 / 终局结算             │
├─────────────────────────────────────────────┤
│  Config 配置层 (ScriptableObject → 纯数据快照) │
│  建筑定义 / 关系矩阵 / 风参数 / 等级表 / 全局参数  │
└─────────────────────────────────────────────┘
```

关键原则：

1. **领域层是唯一真相**。风路怎么走、每一分从哪来，只由领域层计算；表现层只读结果，绝不自己算分。
2. **配置在进入领域层前转成纯数据快照**，领域层不持有 ScriptableObject 引用，保证可单测、可序列化。
3. **事件驱动的表现更新**。领域层每次状态变更（建筑落地、风路重算、覆盖变化）发出领域事件，表现层订阅刷新，避免每帧轮询。
4. **计分产出"分数明细"而不是一个总数**。每次结算返回逐条来源列表（基础分 / 地形 / 某栋邻居 / 物流覆盖 / 惩罚…），直接喂给 §7.4 的预览 UI，也直接喂给单测断言。

## 3. 目录结构规划

```
Assets/
├── Scenes/
│   ├── Main.unity              # 主玩法场景
│   └── Sandbox.unity           # 规则调试沙盒场景
├── Script/
│   ├── Domain/                 # 纯 C# 领域层（asmdef: Game.Domain，noEngineReferences）
│   │   ├── Map/                # 网格、地形、地图元素、地图生成
│   │   ├── Wind/               # 风流传播、合并、循环检测
│   │   ├── Building/           # 建筑实例、合法性校验、锚点归属
│   │   ├── Scoring/            # 计分引擎、分数明细、终局结算
│   │   ├── Logistics/          # 物流覆盖、物流风、物流中心强化
│   │   ├── Progression/        # 等级、建筑组抽取、金币、结束判定
│   │   └── Common/             # 方向、坐标、种子随机、领域事件
│   ├── Config/                 # SO 定义 + 快照转换（asmdef: Game.Config）
│   ├── App/                    # GameSession、摆放流程状态机（asmdef: Game.App）
│   ├── View/                   # 地图/建筑/风/覆盖的渲染（asmdef: Game.View）
│   ├── UI/                     # HUD、建筑组选择、分数预览面板（asmdef: Game.UI）
│   └── Input/                  # Input System 封装（asmdef: Game.Input）
├── Settings/                   # 配置资产实例（.asset）
│   ├── Buildings/              # 每栋建筑一个 BuildingDef 资产
│   ├── Levels/                 # 20 级等级表
│   └── GameRules.asset         # 全局计分/风/物流参数
├── Prefabs/
│   ├── Tiles/                  # 地块表现预制体
│   ├── Buildings/              # 建筑表现预制体（MVP 阶段用几何体白模）
│   └── FX/                     # 风流线、覆盖高亮
├── Tests/
│   └── EditMode/               # 领域层单元测试（asmdef 引用 Game.Domain）
└── Tool/                       # 编辑器工具（地图预览、配置校验器）
```

asmdef 依赖方向：`UI / View / Input → App → Domain ← Config`。`Game.Domain` 勾选 *No Engine References*，从编译层面禁止领域层引用 UnityEngine。

## 4. 核心系统拆解

按设计文档章节映射到模块，含各系统的实现要点与依赖顺序。

### 4.1 地图系统（设计 §5）→ `Domain/Map`

- **网格模型**：方格坐标，每格持有三层信息——地形类型（空岛/绿地/矿藏/浮空/虚空）、建筑占用、途经风段列表。风路挂在格子上但不占建筑位（设计 §5.1）。
- **地图元素**：巨型风车（唯一）、锚点、矿藏、绿地、初始风源、浮空区域，作为生成期写入的静态元素。
- **地图生成器**：接收种子 + 生成参数（各元素数量区间来自配置），输出完整初始地图。MVP 可以先做 2～3 张手工布局的固定地图，随机生成放到 M6（验收第 1 条要求随机生成，但手工图能先支撑规则验证）。

### 4.2 风系统（设计 §8、§9）→ `Domain/Wind`

整个项目**规则最重、必须最先做对**的系统。

- **风的表示**：风源列表 + 全图重算。每次影响风的操作（放风帆、放物流点）后，从所有风源出发重新传播一遍，得到"每格的风段集合"，而不是增量修改——全量重算逻辑简单、无累积误差，MVP 地图规模（预计 ≤ 64×64）下性能完全够。
- **传播规则**：沿当前方向逐格推进，消耗剩余长度；遇风帆按该风帆的左/右 45° 设定转向（不恢复风长）；遇物流点标记为物流风并按限制延长（同点不重复、每股最多两次，设计 §10.5）。
- **合并规则（设计 §8.5–8.6）**：同一格内多股风做向量合成——风力为模长、方向为 45° 吸附；结果风力上限 5、下取整规则待数值化；剩余长度取参与方最大值。合并表中的四个示例必须固化为单元测试用例。
- **循环终止（设计 §8.7）**：每股风记录已途经的风帆/关键节点集合，再次进入即在入口处截断该支路。
- **对外输出**：`每格 → [方向, 风力, 是否物流风]` 的查询接口，供计分、居民区惩罚、船坞收益、表现层箭头渲染共用。

### 4.3 建筑系统（设计 §6、§11、§12）→ `Domain/Building`

- **建筑定义全部来自配置**（见 §5 数据方案），领域层只认建筑 ID + 规则数据，不为每栋建筑写子类；特殊行为（风帆转向、物流点、锚点归属）以"能力标签"挂在定义上，由对应系统识别。
- **合法性校验器**：按定义检查——地形要求（农田→绿地、船坞→浮空区、风帆→有风格、采矿站→矿藏范围内）、占位冲突。返回**具体的非法原因**（供 §7.4 预览高亮）。
- **锚点归属（设计 §12.8）**：船坞落地时按"最近优先、同距取归属数少者"绑定唯一锚点，并按序号套 100%/50%/25%/0% 递减表。

### 4.4 计分引擎（设计 §7、§13～§18）→ `Domain/Scoring`

- **关系矩阵驱动**：真值表 A/B、地图元素交叉表、同类关系表全部转成配置数据（有向关系条目：受益建筑 × 来源建筑 → 分值/上限/半径引用）。计分引擎只做一件事：遍历落点范围内的对象，逐条匹配关系条目，累加成**分数明细**。
- **结算顺序**（对应设计 §7.1 列表）：基础分 → 地形 → 地图元素（巨型风车通用/专属替代逻辑在此处理）→ 有向邻接加减分（含数量上限，如居民区的计数上限表）→ 同类惩罚 → 物流专属邻接分（最多 2 个物流点）→ 物流覆盖分（去重，仅 1 次）→ 风力即时分（风向标乘法、船坞曲线、居民区强风惩罚）→ 特殊效果。
- **预览 = 干跑**：预览调用与真实结算同一条计分管线，只是不落地、不发金币——保证"预览所见即所得"（验收第 4 条）。
- **终局结算（设计 §7.2）**：独立入口，按最终风路/物流状态重算船坞风能奖励与物流网络奖励，只加分不给金币（设计 §3.3）。

### 4.5 物流系统（设计 §10）→ `Domain/Logistics`

- **覆盖状态统一**：本地范围覆盖与物流风覆盖合并为同一个"已接入物流"集合（HashSet 语义），天然保证基础覆盖分只算一次（设计 §10.3–10.4、验收第 16 条）。
- **物流中心**：不产生覆盖，只对指定五类建筑（势能塔/工坊/船坞/粮仓/居民区）发放专属分；自身按范围内物流点数量加分、同类大扣分。
- 覆盖集合在每次风路重算后同步刷新，作为领域事件广播给表现层画覆盖高亮。

### 4.6 等级与建筑组（设计 §3、§4）→ `Domain/Progression`

- 20 级进度、解锁费用表、二选一建筑组抽取（带权重、同组可重复、保底规则）、金币账户（正分按比例转金币、负分不倒扣）、刷新保护机制。
- **结束判定**：完成 20 级 / 无合法落点（对当前手牌全图扫描）/ 金币不足以解锁且手牌为空 / 玩家主动结算，四条件任一触发终局结算。

### 4.7 应用层 → `Script/App`

- `GameSession`：串起"抽组 → 选组 → 逐栋摆放 → 结算发钱 → 解锁下一级"的核心循环状态机（设计 §1.3）。
- 摆放流程状态机：选中建筑 → 拖动预览（实时干跑计分 + 高亮）→ 风帆额外弹左/右转选择 → 确认落地 / 取消。

### 4.8 表现与 UI → `Script/View`、`Script/UI`

MVP 全部用白模和程序化表现，不等美术资源：

- **地图渲染**：地块用色块/简单 Mesh 区分地形；巨型风车、锚点、矿藏用几何体白模。
- **风渲染**：每格风段画方向箭头，颜色映射风力等级（1～5），物流风加描边/变色；这是玩家读懂风系统的关键，投入优先级高于建筑外观。
- **UI 清单（MVP）**：顶部资源条（分数/金币/等级）、建筑组二选一面板、手牌栏、摆放预览明细面板（逐条分数来源，设计 §7.4）、非法原因提示、终局结算面板。

## 5. 数据配置方案（对应设计 §20）

设计 §20 的全部待数值化项收敛为四类 ScriptableObject：

| 配置资产 | 内容 | 对应设计章节 |
|---|---|---|
| **BuildingDef**（每建筑一个） | ID、名称、基础分、作用半径、地形要求、能力标签（风帆/物流点/物流中心/船坞…）、同类惩罚半径与数值、风力收益曲线、各邻接计数上限 | §11、§12、§15 |
| **RelationTable**（全局一个） | 全部有向邻接关系条目（真值表 A/B + 单向表 + 双向表 + 负面表的数据化） | §13、§16、§17、§18 |
| **LevelTable**（全局一个） | 20 级解锁费用、每级建筑组池与权重、保护机制参数 | §4 |
| **GameRules**（全局一个) | 巨型风车通用/专属分、初始风参数、风合并参数、物流覆盖范围/覆盖分/延长值、锚点递减表、分数转金币比例、终局奖励参数、地图生成参数 | §5、§6、§8、§10、§20 |

配套两个编辑器工具（放 `Assets/Tool`）：

1. **配置校验器**：检查关系表与真值表一致性（如"双向关系必须在两个方向各有一条"、"§21 已确认决策不被配置违反"），一键报告。
2. **数值总览窗口**：把所有 BuildingDef 的关系汇总回真值表形态展示，供策划对照设计文档核对。

## 6. 里程碑计划

每个里程碑以"可运行/可测试的交付物"收口，M1～M4 是纯逻辑优先，表现层最小化。

### M0 · 工程骨架（0.5 周）

- 建目录结构与 6 个 asmdef，`Game.Domain` 关闭引擎引用；
- 建 Main / Sandbox 场景、Cinemachine 环绕相机、Input Action Map；
- EditMode 测试工程跑通第一条空测试；
- 交付：空转的工程骨架，`git` 初始提交。

### M1 · 地图 + 摆放闭环（1 周）

- 网格模型、手工固定地图（含全部 7 类初始元素）；
- 建筑定义配置 + 合法性校验（地形要求、占位）；
- 摆放流程状态机 + 白模落地表现；
- 交付：能在地图上合法/非法地摆建筑，非法时给出原因。
- 覆盖验收：#3。

### M2 · 计分引擎（1.5 周）

- 分数明细结构、关系矩阵配置、有向邻接结算、同类惩罚、巨型风车通用/专属替代、计数上限；
- 金币转化、等级解锁、二选一建筑组、结束判定；
- 预览面板（干跑明细 + 加減分对象高亮）；
- 交付：不含风的完整 ISLANDERS 式可玩循环（20 级打通）。
- 覆盖验收：#2、#4、#5、#6、#7、#25。

### M3 · 风系统（1.5 周）

- 风传播、风帆左右 45° 转向、向量合并（含 §8.5 四示例）、长度取大、5 级封顶、循环截断；
- 风渲染（方向箭头 + 风力颜色）；
- 风相关计分接入：风帆即时分、船坞风能曲线、船坞无风惩罚、居民区 4/5 级强风惩罚；
- 交付：风路可规划、可预测，改风帆立即看到全图风路变化。
- 覆盖验收：#8、#9、#10、#11、#12、#13、#20（风部分）、#21。

### M4 · 物流系统（1 周）

- 本地覆盖 + 物流风远程覆盖统一状态、覆盖分去重、专属邻接分（≤2 物流点）与覆盖分叠加、延长风长限制、物流点同类惩罚；
- 覆盖范围渲染；
- 交付：物流网络完整可玩。
- 覆盖验收：#14、#15、#16、#17、#18。

### M5 · MVP 收口（1 周）

- 锚点归属 + 同锚点递减、船坞孤立惩罚；
- 终局结算（即时分与终局网络分分离）+ 结算面板；
- 首批 8 建筑（农田/风车/采矿站/工坊/居民区/风帆/物流点/船坞，设计 §19.2）数值初调；
- 交付：**可对外试玩的 MVP**，逐条核对设计 §19.3 的 8 个验证目标。
- 覆盖验收：#22、#23、#24。

### M6 · 完整版扩展（视 MVP 验证结果，约 2 周）

- 第二批 7 建筑（势能塔/粮仓/餐厅/商店/市民中心/物流中心/风向标）；
- 随机地图生成器（验收 #1）；
- 保护机制完善（刷新/保底/跳过）、数值平衡轮、表现打磨。

> 总计 MVP（M0～M5）约 6.5 周；含完整版约 8.5 周。单人开发按此排期，多人可将 M2 与 M3 并行（计分与风系统仅在"风力即时分"处耦合）。

## 7. 测试策略

### 7.1 EditMode 单元测试（主力）

领域层零引擎依赖，规则全部用单测锁定。必测清单：

- **风**：直线传播长度耗尽；风帆左/右转向；§8.5 合并示例表 4 条；合并长度取大；5 级封顶；循环截断；物流点延长的两条限制。
- **计分**：真值表 A/B 抽样逐条（至少覆盖每种符号各一例）；单向关系不反向生效（工坊给风车加分、风车不给工坊加分）；巨型风车专属替代通用；居民区计数上限表；同类惩罚。
- **物流**：双物流点覆盖同一建筑只算一次覆盖分；本地覆盖与物流风覆盖不叠加；专属分与覆盖分叠加；物流中心只强化指定五类。
- **船坞**：锚点归属两条规则；递减表 100/50/25/0；0 级风惩罚；孤立惩罚。
- **进程**：金币转化（负分不倒扣）；四种结束条件；终局奖励不给金币。

### 7.2 配置校验（编辑器工具）

每次改配置资产后一键校验：关系表对称性、§21 的 18 条已确认决策不被违反、数值缺失检测。

### 7.3 沙盒场景手测

Sandbox 场景提供作弊面板：直接给金币、跳级、任意刷建筑、手动放风源——用于快速搭出边界场景（多风合流、超长物流链）做人工验证。

## 9. 风险与开放问题

| # | 风险/问题 | 影响 | 应对 |
|--:|---|---|---|
| 1 | **风合并的具体数学**：向量合成后风力"下取整还是四舍五入"、非整数模长如何映射 1～5 级，设计未定 | 影响可预测性（MVP 验证目标 3） | M3 开工前定一版规则写进 GameRules 注释，用 §8.5 示例表反推校准，做成可配置策略 |
| 2 | **风相遇的判定粒度**：同格相遇即合并，还是仅同格同向前进才合并（垂直交叉是否互不干扰） | 影响风路规划深度 | 建议 MVP 采用"同格即合并"，简单可读；沙盒实测后再定 |
| 3 | **"范围"的度量**：设计中大/中/小范围未定义是切比雪夫、曼哈顿还是欧氏距离 | 影响所有邻接计分 | 方格网格建议统一切比雪夫距离（与八方向一致），数值配置只填半径 |
| 4 | 内置管线画风流/覆盖特效表现力有限 | 表现层 | MVP 用 LineRenderer + 顶点色够用；若效果不满意 M6 评估切 URP（2022.3 切换成本低，越早越好） |
| 5 | 全量重算风路在超大地图上的性能 | 性能 | MVP 地图 ≤ 64×64 无风险；若后续扩图，再做脏区域增量重算 |
| 6 | 数值冷启动：§20 全部数值无初值 | 可玩性 | M2/M3 各留半天"拍初值"，以船坞曲线（唯一有数值的表）为锚推算其他建筑量级 |
| 7 | 风帆落在"多股风同格"处时左右转以哪股为入风 | 规则歧义 | 建议：风帆对经过该格的每股风独立生效，各自按其入风方向转 45°；写单测锁定 |
